# Bridge prototype

## How to test (5 lines)
1. Open the Artifact link in claude.ai (live AI runs on your own Claude account), or run `./build.sh`, open `index.html`, and add an Anthropic API key under Settings (gear icon).
2. Click **Try demo**: miss at least one of the 3 quick-check questions, read the bridge, tap highlighted words in the passage, take the 3-question check, then answer the survey. Answer all 3 correctly to see the bridge step skipped.
3. Pick **中文** or **Español** before starting to get home-language glosses (toggle them on the Bridge and Reread screens). **English only** shows none.
4. Click **fill in a statistics example** (or paste your own text), then **Find what it assumes**. This step needs live AI.
5. Footer → **Evidence log** for averages and JSON/CSV export. Header → **Teacher** for the class view (**Load example class data** if it's empty). Settings → **Testing tools** to simulate broken AI output or shift the clock so spaced reviews come due.

## Files
- `app.html`: the app, and the source published as the Artifact. It has no `<html>`/`<head>` wrapper.
- `build.sh`: wraps `app.html` into a standalone `index.html` for local use.
- `index.html`: generated by `build.sh`.

## Known limitations
- **Live AI wasn't run end to end by the builder.** The demo, the UI, the API request shape (against a mocked endpoint) and the claude.ai capability calls (against a simulated `window.claude`) were all tested in a browser. Model output quality was checked by having Claude answer the app's exact prompts for two statistics passages and validating the replies with the app's own validators. Run acceptance tests 2 and 4 once yourself in claude.ai.
- **Live AI in the Artifact needs a Claude account.** Each viewer's own Claude account answers the calls. Students without one can only use **Try demo**, unless you host `index.html` with an API key.
- **The API-key mode calls Anthropic straight from the browser.** That's fine for testing on your own machine. A public deployment needs a small server so the key isn't exposed.
- **Data stays on one device.** Sessions, reviews and the teacher view live in that browser's localStorage. Testers have to export and send their files. The teacher view only sees students who used the same device, so a classroom pilot needs a shared device or a shared database.
- **AI content isn't reviewed by a person.** Answer keys, explanations and glosses come from the model. Cross-checking `answer_text` against `correct_index` catches index slips, not wrong math. The demo's saved Chinese and Spanish glosses were written by Claude and haven't been checked by a native-speaking teacher.
- **The first analysis of a passage is reused.** Every later student on the same device sees the same prerequisites and questions, which keeps class numbers comparable. A weak first analysis repeats until you use **Delete all data**.
- **Language gaps are under-sampled.** Only the top 3 prerequisites get a quick-check question. Academic-language terms often rank 4th or 5th, so they show up in the teacher view less often than they occur. Students can still tap **Explain this to me** on any marked word.
- **The guardrails are prompt-based.** The no-final-answer rule and the "say when unsure" rule live in the prompts. In the simulated homework test nothing leaked, but no code checks for a leaked answer.
- **Highlighting depends on the AI quoting the passage exactly.** If it doesn't, the term appears under "Also assumed" instead of being highlighted.
- **Math is plain Unicode text.** Passages full of LaTeX show the raw markup.
- **Time spent is wall-clock time** from start to survey, so it includes idle time.
- **The progress rail shows 5 phases:** Passage, Gaps, Check, Bridge (which includes the reread), and Practice (which includes the survey). Together they cover the 7 loop steps.
- **Example class data is made up.** It is labelled everywhere it appears and left out of session exports by default.
